# Benchmark 10: make the compiler an optimising one (the full principled org, against one agent)

with SQLite first, design B10" and "$300 approved, go ahead" (2026-10-24); "victories happen after many many failures
… if we just change our mind based on data that is not innovation that is accounting" · design:
[PRINCIPLES.md](../../PRINCIPLES.md), all of it

## Why v2 (v1 is in git history, commit "B10 design: compile SQLite")

v1 asked the arms to make the compiler build SQLite 3.53.4 and pass a hidden SQL corpus. Building the harness showed
that **B9 V's compiler already does it**: once given the system headers SQLite's Unix build needs, it compiles the
whole amalgamation (269,668 lines) in 18 s, and the result passes 170 of 170 corpus scripts byte for byte. The task
was solved at the start. What is far from solved is the **code it generates**. On the same workload, counted by
valgrind:

| Build of SQLite + sqlrun | Instructions executed (callgrind, `small.sql`) | Wall time (`heavy.sql`, 300k rows) |
|---|---|---|
| gcc -O0 | 1,144,043,908 | 5.18 s |
| **our compiler (start)** | **1,048,938,538** (identical on every run) | **3.67 s** |
| gcc -O2 | 568,105,578 | 1.85 s |

Our compiler's SQLite executes **1.85× gcc -O2's instructions**. Closing that gap means turning a straightforward
code generator into an optimising compiler: an intermediate representation, register allocation, instruction
selection, constant folding and propagation, inlining, dead-code elimination, better calling sequences, peephole
work. That is long, many-area work, the kind of work the org thesis is about.

## The thesis, and what this benchmark is for

**Thesis (held, not up for a vote on one result):** an organisation of agents beats a single agent on work too big
and too long for one mind, as human institutions beat individuals on such work. B8 and B9 did not test it (a bounded
task that fit one context, refereed by wall-clock time that parallel workers disturb). B10 gives the org its reasons:

- **long horizon and many areas:** an optimising compiler is a sequence of passes, each a specialism, built in layers
  where each pass makes the next pay off;
- **an undisturbable referee:** instruction counts under valgrind do not depend on machine load, so parallel workers
  measure as precisely as a lone agent (B9's binding handicap removed);
- **more than one context:** the compiler (about 90k tokens, growing), the hot paths of SQLite it must compile well
  (the VDBE, B-tree and pager: several hundred thousand tokens), and the generated assembly (5.5 MB, about 1.5M tokens)
  do not fit one context together; the work must be read selectively and remembered.

It is one step of a programme: if the org loses, we change the design and run again; the predictions say what we
expect, so a loss says *what* to change.

## The task

Starting from B9 V's compiler (passes W1-W7, builds Lua and SQLite), **make the code it generates faster**: the SQLite
it builds should execute as few instructions as possible on SQL workloads it has never seen, while staying exactly
correct. Source: SQLite 3.53.4's amalgamation as vendored in the npm package better-sqlite3 13.0.3
(`deps/sqlite3/`; sqlite.org and GitHub are not reachable from the container; npm is).

Provided (`material/`): the header set (glibc's x86-64 layouts; checked field by field against the system headers,
and SQLite built against them gives the same output as against the system's); the compile options
(`opts.txt`: `SQLITE_THREADSAFE=0`, `OMIT_LOAD_EXTENSION`, `OMIT_WAL`, `DEFAULT_MEMSTATUS=0`, `MAX_MMAP_SIZE=0`,
`TEMP_STORE=3`, …); `sqlrun.c` (runs one statement per line against an in-memory database and prints column names,
rows, change counts and errors); the corpus generator's visible output; the build line
(`ccc -I include -I . <opts> sqlite3.c` and `sqlrun.c`, then `gcc sqlite3.s sqlrun.s -o sqlrun -lm`).

## The score (the referee)

- **Primary: the instruction ratio**, the geometric mean over the hidden workloads of (instructions executed by the
  arm's SQLite) ÷ (instructions executed by gcc -O2's SQLite), counted by `valgrind --tool=callgrind`. Lower is better;
  the start is about 1.85; gcc -O2 is 1.0; below 1.0 is possible in principle.
- **Workloads:** 12 heavy SQL scripts (bulk insert, index build, sort, GROUP BY, joins, window functions, LIKE and
  string functions, JSON, recursive CTEs, triggers, updates), 6 visible (given to the agents with their gcc -O2 counts)
  and 6 hidden (different scripts of the same kinds, never shown).
- **Gate** (a version that fails any of it scores 2.0):
  - the hidden SQL corpus: 3,000 scripts (deterministic generator, seed hidden; the agents get 600 visible ones)
    with output identical to gcc's build;
  - W1-W7's hidden runners;
  - Lua builds and passes its test files;
  - compiling `sqlite3.c` takes at most 60 s (the start: 18 s), and every compile stays deterministic.
- **Reported:** wall time of the built SQLite on `heavy.sql` on the quiet machine at the end (against gcc -O0 and -O2),
  the compile time, and each kept change's gain.
- Both arms run **at once**: instruction counts are load-independent, and correctness checks are too.

## The arms

Same model family, tools, rules, sandbox and caps for both: **$150 and 6 active hours each** (founder-approved $300 in
total); the same tree and the same task text; both may use the visible workloads and corpus, gcc and valgrind as
measuring tools (never gcc as the compiler; no copying gcc's output), and the fast judge.

**V, one agent.** One Agent SDK session (the SDK compacts its context when it fills), told the whole task, in charge of
its own plan; continued with "go on" turns until the budget or time runs out.

**O, the full principled org** (PRINCIPLES.md, nothing left out that B9c left out):

| Element | How |
|---|---|
| Autonomy (1) | nobody assigns work; each member reads what it chooses, plans its own focus, changes course on evidence |
| Diversity (2) | 4 workers with generic temperaments (measure, bold, sceptic, lean); **each builds its own context** (no shared parent session, so no single witness); two of the four (sceptic, lean) on a second model (Sonnet 5.5): another source, and cheaper (the proportion principle: "cheaper models for some members"; a warm Opus worker cost $0.40-0.50 a minute in B9c, so four of them would spend the $150 in under two rounds) |
| Full context (3) | each worker's session persists across all rounds (warm); the SDK compacts it when needed |
| Shared, organised learning (4) | the findings board (findings, dead ends, hypotheses; evidence and wrong-if required) by area, plus **practices with beliefs** (K38): a hand-in names the practices it used; code updates each practice's belief from whether that merge was kept and what it gained |
| Independent referee and credit (5) | after each round code merges the workers' heads into main one at a time (best first); a merge stays only if the gate passes and the visible instruction ratio does not rise; credit = its fall; every result goes on the board |
| Roles and hierarchy | **architect** (fixed role, its own warm session): owns the interfaces between passes (the IR, if one is introduced; the AST and type representations), resolves merge conflicts, settles disputed claims, writes each round's intent from the profile ("where the instructions go now"); assigns no work |
| Ownership as stewardship | **earned**: after round 2, the member with the most kept credit in an area becomes its steward (code decides, from the referee's record); a steward keeps `docs/areas/<area>.md` (its playbook), reviews every kept merge in its area the next round and may ask the architect to revert one with evidence, and is still free to work anywhere |
| Coverage and reach | claims for short focus (as B9c); stewards give the floor; the coverage map per area (who looked, who changed it, kept credit, reverts) every round, shown to the architect |
| Proportion | 4 workers, not more; the org stops early when two rounds in a row gain under 1% |

Rounds of 45 minutes; integration by code, the referee and (on conflicts) the architect; a round starts only if the budget left covers its expected cost (about $40), so about 3-4 rounds fit the $150. Merge checks (build, visible corpus, visible workloads) run after each merge; the visible W1-W5 and Lua check runs on main once per round, and a failure reverts that round's merges from the last until it passes.
Areas for the coverage map, by file: frontend (lexer, preproc), parser and types, codegen (and any new IR,
register-allocation or optimisation files), driver.

## Predictions (committed before any run)

| # | Prediction | Wrong if | Prior |
|---|---|---|---|
| B10-1 | O's final hidden instruction ratio is at least 10% lower than V's (O ≤ 0.9 × V) | O > 0.9 × V | 50% |
| B10-2 | both arms improve on the start by at least 15% (ratio ≤ 1.57) | either does not | 70% |
| B10-3 | V's context compacts at least twice | fewer | 75% |
| B10-4 | O's ratio falls in every round it runs (at least 3); V's curve flattens earlier (its last third of commits gains less than its first third) | O has a round without a fall, or runs fewer than 3 | 50% |
| B10-5 | O's kept work includes a new pass that another worker's later kept work builds on (e.g. an IR, then register allocation on it) | no such chain | 45% |
| B10-6 | stewards emerge in at least 2 areas, and a steward's review leads to at least one revert or fix | fewer | 45% |
| B10-7 | the referee reverts at least 2 of O's merges | fewer | 70% |
| B10-8 | the two Sonnet workers together earn at least 25% of O's kept credit | less | 40% |
| B10-9 | neither arm reaches gcc -O2 (ratio 1.0) | an arm does | 85% |
| B10-10 | the gains are general: the hidden ratio is within 5% of the visible one for both arms | outside | 70% |

**If O loses**, the next design changes the most likely cause first: per-worker budget too thin; the architect's
intent too vague to spread the workers; stewards too late; the second model too weak. "A philosophy of emergence
should be willing to lose an A/B test", and willing to run the next one.

## What has to be built first (operator, before any run)

1. Done: the header set (layouts checked; SQLite against it equals SQLite against the system headers), `sqlrun.c`,
   the corpus generator (deterministic: 170 of 170 scripts stable across runs and identical across header sets).
2. The workloads: 12 heavy scripts (6 visible, 6 hidden), each about 0.5-1.5 billion instructions under gcc -O0.
3. The judge (fast: build, visible corpus, visible workloads under callgrind; full: hidden corpus, hidden workloads,
   W1-W7 and Lua gates), sandboxed as B9's, with a lock only around the build (instruction counts need none).
4. The O harness on B9c's code: persistent warm workers that each build their own context, the architect session,
   stewards by code, practice beliefs, the coverage map, a second model for one worker, and the cost fix.
5. A fake dry run of both arms, then a one-round real smoke test of O ($10 cap).

Cost: up to $300 for the two arms, plus about $10 for the smoke test. Time: preparation about 3 hours more; the run 6
active hours (both arms at once); write-up 1 hour.
